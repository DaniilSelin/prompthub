# Тест-план проекта prompthub-develop-tests

## 1. Цель документа
Определить стратегию и набор проверок для всех вариантов использования (ВИ-1 ... ВИ-17), включая уже реализованные, частично реализованные и пока не реализованные функции.

## 2. Объект тестирования
Проект: библиотека хранения и версионирования промптов на SQLite.
Ключевые подсистемы:
- Инициализация хранилища и схема БД
- CRUD промптов
- Версионирование (snapshot + delta)
- Теги и model_tags
- Поиск и фильтрация
- Получение промпта для использования

## 3. Тестовая стратегия
Уровни тестирования:
- Unit: операции дельт, фильтры, построение SQL, проверки бизнес-логики отдельных методов.
- Integration: взаимодействие facade -> repository -> SQLite (in-memory и file-based БД).
- Contract/API: проверка ожидаемого поведения публичных методов facade.
- Regression: повторный запуск набора после изменений в схемах, фильтрах, версионировании.

Типы проверок:
- Позитивные сценарии
- Негативные сценарии (ошибки валидации, отсутствующие сущности)
- Граничные сценарии (пустые данные, дубликаты, большие тексты)
- Конкурентный доступ (минимум smoke-проверки блокировок/консистентности)

Pytest-конвенции:
- Использовать маркеры: `@pytest.mark.unit`, `@pytest.mark.integration`, `@pytest.mark.contract`.
- Зарегистрировать маркеры в `pytest.ini` (чтобы исключить `PytestUnknownMarkWarning`).
- Для известных дефектов текущей реализации использовать `@pytest.mark.xfail(strict=True, reason=...)`.
- Для нереализованных ВИ использовать `@pytest.mark.skip(reason=...)` до появления API.
- Для проверок ошибок ОС/доступа использовать стабильно воспроизводимый сценарий (mocker/monkeypatch), чтобы избежать flaky-тестов.

## 4. Окружение
- ОС: Windows
- Python: 3.10+ (минимум по требованиям; в CI рекомендуется фиксировать конкретную версию)
- БД: SQLite (in-memory для unit/integration, файловая для smoke)
- Инструменты: pytest, coverage, ruff (по возможности)

## 5. Критерии входа и выхода
Критерии входа:
- Стабильная схема БД и фиксированная версия Python
- Определены ожидаемые ошибки/исключения по каждому ВИ

Критерии выхода:
- 100% прохождение критичных проверок текущей реализации: ВИ-1, ВИ-2, ВИ-3, ВИ-16
- Для ВИ с известным расхождением с требованиями (ВИ-2, ВИ-3, ВИ-8, ВИ-16): есть contract-тесты, фиксирующие требуемое поведение
- Для нереализованных ВИ: готовы contract-тесты с expected behavior

## 6. Границы покрытия (as-is / to-be)
- As-is (текущее покрытие integration/regression): сценарии, которые уже реализованы в коде (`Storage`, `Prompt`, `PromptRepo`, `PromptGroup`, SQL filters).
- To-be (contract): сценарии из требований, для которых в текущем коде нет публичного API или нет инфраструктуры (адаптеры, тарифы, compare API, list_tags API).
- Для каждого to-be кейса в автотестах использовать `@pytest.mark.contract` + `@pytest.mark.skip(reason=...)` до реализации API.

## 7. Набор тестов по каждому варианту использования

### ВИ-1. Инициализация хранилища
Проверки:
- Создание новой БД при отсутствии файла.
- Создание обязательных таблиц и индексов.
- Проверка PRAGMA (journal_mode, foreign_keys) для корректной конкурентности и каскадных удалений.
- `foreign_keys` проверять на том же `sqlite3.Connection`, который используется `Storage` (PRAGMA connection-scoped).
- Повторная инициализация без потери данных.
- Ошибка при недоступном пути/правах.

### ВИ-2. Создание промпта
Проверки:
- Успешное создание prompt и первой версии (snapshot) в двухшаговом сценарии: create_prompt + add_version.
- Контракт уникальности имени промпта (требование) и фиксация текущего поведения (дубли допускаются).
- Корректность метаданных (author, created_at).
- Контракт на создание с содержимым сообщений и валидацию role/content (требование, сейчас не реализовано отдельным API).

### ВИ-3. Изменение промпта
Проверки:
- Создание новой версии с корректным seq.
- Формирование delta для insert/delete/replace.
- Snapshot на каждом N шаге (snapshot_interval).
- Обработка сценария без изменений (контракт: новая версия не должна создаваться).

### ВИ-4. Удаление промпта
Проверки:
- Полное удаление prompt + versions + changes + связи тегов (при включенных foreign keys).
- Поведение при удалении несуществующего промпта.

### ВИ-5. Список всех промптов с ценой (частично)
Проверки текущего состояния:
- Возврат списка промптов и основных метаданных.

Планируемые проверки после реализации:
- Подсчет токенов актуальной версии.
- Расчет стоимости по model_tags и тарифам.
- Поведение при отсутствии тарифа для части моделей.

### ВИ-6. История версий
Проверки:
- Возврат всех версий выбранного промпта.
- Сортировка по seq (возрастание).
- Поля в ответе текущего API: версия (seq), дата, описание.
- Проверка, что история версий не включает сборку/реконструкцию snapshot и chain delta (это отдельный сценарий ВИ-16).

Примечание для pytest:
- Проверку состава полей оформить отдельным contract-тестом с `@pytest.mark.contract`.

### ВИ-7. Сравнение версий (реализовано)
Реализованы два публичных метода:
- `compare_versions(name_a, name_b) -> VersionLineDiff` — построчный diff в формате unified diff (git-style).
- `compare_versions_chars(name_a, name_b) -> VersionDiff` — посимвольный diff через `SequenceMatcher`.

Проверки:
- Line diff между двумя различными версиями содержит изменения (`has_changes=True`).
- Line diff для одной и той же версии пуст (`has_changes=False`, `unified()==""`).
- Char diff возвращает `DiffChunk` с корректными тегами и текстами.
- Char diff для идентичных версий: `has_changes=False`, `only_changes()==[]`.
- Совокупность чанков char diff восстанавливает оба оригинальных контента.
- Ошибка `ValueError` при несуществующей версии в обоих методах.

### ВИ-8. Восстановление версии (реализовано)
Реализованы два метода:
- `rollback(name, steps_back, name_rollback_version, author)` — мягкий откат: создаёт новую версию с контентом целевой, история сохраняется.
- `rollback_hard(name, steps_back)` — жёсткий откат: удаляет все версии после целевой.

Проверки:
- Мягкий откат по имени версии добавляет новую версию с содержимым целевой.
- Мягкий откат по steps_back создаёт новую версию с корректным контентом.
- История сохраняется после мягкого отката (старые версии не удаляются).
- Жёсткий откат по имени удаляет все версии после целевой.
- Жёсткий откат по steps_back удаляет нужное количество версий.
- Жёсткий откат выбрасывает ValueError для несуществующего имени версии.
- Ошибка при некорректном количестве шагов (steps_back >= len(versions) или < 0).

### ВИ-9. Добавление тега
Проверки:
- Добавление нового prompt-тега.
- Игнорирование дублей (INSERT OR IGNORE).
- Создание тега в словаре tags при отсутствии.

### ВИ-10. Удаление тега
Проверки:
- Удаление существующей связи prompt-tag.
- Идемпотентность удаления отсутствующей связи.

### ВИ-11. Добавление model_tag
Проверки:
- Добавление тега типа model.
- Отсутствие дубликатов связей.

Планируемые проверки после доработки требований:
- Валидация model_tag по наличию тарифа.
- Ошибка для неподдерживаемых model_tag (согласно требованиям).

Примечание:
- В документе требований есть конфликт формулировок для кейса "model_tag без тарифа" (warning vs ошибка). Для contract-тестов здесь принят вариант из функциональных требований: возвращается ошибка.

### ВИ-12. Удаление model_tag
Проверки:
- Удаление существующей связи model_tag.
- Contract-проверка: ошибка для удаления отсутствующей связи (согласно требованиям).

### ВИ-13. Просмотр всех тегов (не реализовано)
Планируемые проверки:
- Возврат уникального списка tags.
- Корректная работа при пустом словаре тегов.
- Опциональная сортировка.

### ВИ-14. Поиск промптов по тегу
Проверки:
- with_tag: текущий API возвращает версии, принадлежащие промптам с указанным тегом.
- without_tag: исключение по тегу.
- Проверки ограничены двумя пользовательскими функциями: with_tag и without_tag.
- Проверка формата результата выполняется в рамках integration-сценариев with_tag/without_tag.

### ВИ-15. Поиск промпта по имени
Проверки:
- Поиск существующего имени.
- Поведение для несуществующего имени (ошибка/None согласно API).

### ВИ-16. Получение промпта для использования
Проверки:
- Получение контента конкретной версии по имени версии (текущий API).
- Реконструкция содержимого из snapshot + chain delta.
- Ошибка для несуществующей версии.

Планируемые проверки после реализации адаптеров:
- Contract-проверка требуемого метода get_prompt(name, version=None, adapter_type=None).
- Конвертация в целевой adapter_type.
- Ошибка для неподдерживаемого adapter_type.

### ВИ-17. Обновление тарифов моделей (не реализовано)
Планируемые проверки:
- Загрузка и upsert тарифов.
- Валидация формата тарифов.
- Обработка недоступности внешнего источника.
- Транзакционность обновления.

## 8. Минимальный обязательный регрессионный набор
- ВИ-1, ВИ-2, ВИ-3, ВИ-16 (критичный путь текущей реализации)
- ВИ-8 как блокирующий дефектный сценарий, выполняемый с `@pytest.mark.xfail(strict=True)` до исправления реализации rollback
- ВИ-9, ВИ-10, ВИ-14 (тегирование и поиск)
- Smoke по целостности БД после удаления/отката

## 9. Дефекты и отчетность
Для каждого дефекта фиксировать:
- Идентификатор ВИ
- Шаги воспроизведения
- Фактический результат
- Ожидаемый результат
- Severity/Priority
- Версию кода/коммита

## 10. План внедрения автотестов
Этап 1 (сразу):
- Unit для query-слоя: в первую очередь наследники BaseQuery, затем Condition.
- Unit для filters, operations, build_changeset.
- Integration для storage/repo на sqlite :memory:.

Этап 2:
- Regression suite для критичных ВИ.
- Набор contract-тестов для ВИ-2, ВИ-3, ВИ-5, ВИ-6, ВИ-7, ВИ-8, ВИ-11, ВИ-12, ВИ-13, ВИ-16, ВИ-17 (как спецификация требуемого поведения).

Этап 3:
- После реализации недостающих ВИ перевести contract-тесты в полноценные integration.

## 11. Дополнительно: что считать готовностью реализации ВИ
ВИ считается закрытым только если:
- Есть рабочий публичный метод facade/клиента.
- Есть позитивные и негативные тесты.
- Есть проверка граничных сценариев.
- Набор включен в регрессию.
