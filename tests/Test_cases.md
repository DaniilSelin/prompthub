## Детализированные test cases

Формат кейса:
- ID: уникальный идентификатор теста
- Тип: unit/integration/contract
- Приоритет: High/Medium/Low
- Предусловия: начальное состояние
- Шаги: последовательность действий
- Ожидаемый результат: проверяемый итог

### ВИ-1. Инициализировать хранилище

**TC-UC01-001: Создание новой БД и схемы**
- Тип: integration
- Приоритет: High
- Предусловия: путь к новому временному файлу БД, файл отсутствует.
- Шаги:
1. Создать объект Storage с новым db_path.
2. Подключиться к SQLite и прочитать sqlite_master.
3. Проверить наличие таблиц prompts, prompt_versions, prompt_changes, tags, prompt_tags.
4. Проверить `PRAGMA journal_mode`.
5. Проверить `PRAGMA foreign_keys` на соединении `storage._conn`.
- Ожидаемый результат: файл БД создан; все таблицы и индексы из схемы присутствуют; `journal_mode` и `foreign_keys` соответствуют целевому режиму проекта.

**TC-UC01-002: Повторная инициализация без потери данных**
- Тип: integration
- Приоритет: High
- Предусловия: существующая БД, в ней есть хотя бы один prompt.
- Шаги:
1. Инициализировать Storage на существующем пути.
2. Выполнить get_prompt по ранее созданному имени.
3. Повторно инициализировать Storage на том же пути.
4. Снова выполнить get_prompt.
- Ожидаемый результат: данные сохраняются, схема не ломается, повторная инициализация проходит без ошибок.

**TC-UC01-003: Ошибка при недоступном пути**
- Тип: integration
- Приоритет: Medium
- Предусловия: путь, в который нельзя записать файл.
- Шаги:
1. Смоделировать ошибку открытия БД через monkeypatch/mocker (`sqlite3.connect` выбрасывает `sqlite3.OperationalError`).
2. Попытаться создать Storage с db_path.
- Ожидаемый результат: выбрасывается контролируемая ошибка подключения/доступа к файлу без зависимости от особенностей ОС.

### ВИ-8. Восстановить промпт из предыдущей версии

**TC-UC08-001: Мягкий откат по имени версии**
- Тип: contract
- Приоритет: High
- Предусловия: есть версии v1, v2, v3.
- Шаги:
1. Вызвать rollback(name="v1", name_rollback_version="rollback_to_v1").
2. Проверить, что появилась новая версия с seq = previous_latest + 1.
3. Проверить, что name новой версии == "rollback_to_v1".
4. Проверить, что контент новой версии равен контенту v1.
5. Проверить, что v1..v3 не удалены.
- Ожидаемый результат: история дополнена новой версией отката, старые версии сохранены.

**TC-UC08-002: Мягкий откат на N шагов назад**
- Тип: contract
- Приоритет: High
- Предусловия: есть не менее 4 версий.
- Шаги:
1. Вызвать rollback(steps_back=2, name_rollback_version="rollback_steps_2").
2. Проверить, что seq новой версии == previous_latest + 1.
3. Проверить, что контент соответствует версии на 2 шага назад.
4. Проверить, что все предыдущие версии не удалены.
- Ожидаемый результат: корректная новая версия отката без разрушения истории.

**TC-UC08-003: Некорректное количество шагов**
- Тип: integration
- Приоритет: Medium
- Предусловия: есть 2 версии.
- Шаги:
1. Вызвать rollback(steps_back=999) и rollback(steps_back=-1).
- Ожидаемый результат: выбрасывается ValueError с сообщением "Некорректное количество шагов".

**TC-UC08-004: Жесткий откат по имени версии удаляет более поздние версии**
- Тип: integration
- Приоритет: High
- Предусловия: есть версии v1, v2, v3, v4.
- Шаги:
1. Вызвать rollback_hard(name="v2").
2. Проверить, что версий стало 2.
3. Проверить, что в истории остались только v1 и v2.
4. Убедиться, что контент v2 корректен.
- Ожидаемый результат: версии v3 и v4 удалены, v1 и v2 сохранены с правильным контентом.

**TC-UC08-005: Жесткий откат по steps_back**
- Тип: integration
- Приоритет: High
- Предусловия: есть версии v1, v2, v3.
- Шаги:
1. Вызвать rollback_hard(steps_back=1).
2. Проверить количество оставшихся версий.
3. Проверить, что последняя версия - v2 с правильным контентом.
- Ожидаемый результат: v3 удалена, осталось 2 версии.

**TC-UC08-006: Жесткий откат выбрасывает ошибку для несуществующей версии**
- Тип: integration
- Приоритет: Medium
- Предусловия: prompt с одной версией.
- Шаги:
1. Вызвать rollback_hard(name="v999").
- Ожидаемый результат: выбрасывается ValueError.
