# Общее описание ВИ

# ВИ
1. Инициализировать хранилище: подключиться к библиотеке, передав путь к файлу базы данных (SQLite). Если файл по указанному пути не существует, система должна создать его и инициализировать структуру таблиц.
2. Создать промпт: создать новый именованный промпт с указанием структуры ролей (system, user, assistant и т.п.) и сохранить его в хранилище как первую версию.
3. Изменить промпт: зафиксировать измененное содержимое существующего промпта как новую версию, не затирая предыдущие.
4. Удалить промпт: полностью удалить промпт и все его версии из хранилища.
5. Просмотреть список всех промптов: получить список всех промптов, хранящихся в библиотеке, дополненный рассчитанной стоимостью промпта для каждой модели из model\_tags.
6. Просмотреть историю версий: получить список всех версий конкретного промпта с метаданными.
7. Сравнить версии промпта: получить разницу между двумя указанными версиями одного промпта, чтобы видеть что именно изменилось.
8. Восстановить промпт из предыдущей версии.
9. Добавить тег к промпту: присвоить промпту один или несколько тегов для последующей категоризации и поиска.
10. Удалить тег с промпта: снять ранее присвоенный тег с промпта.
11. Добавить тег модели к промпту: присвоить промпту один или несколько тегов идентифицирующих LLM модели для расчета стоимости обращения.
12. Удалить тег модели с промпта: снять ранее присвоенный тег с промпта.
13. Просмотреть все теги: получить список всех тегов, которые используются в хранилище.
14. Найти и вернуть промпты по тегу: получить список промптов с их метаданными, которым присвоен указанный тег.
15. Найти промпт по названию: найти промпт по имени.
16. Получить промпт для использования: извлечь актуальную (или указанную) версию промпта в виде сырых данных (dict/json) или в виде нативного объекта поддерживаемого фреймворка.
17. Обновить тарифы моделей: получить и сохранить в системе актуальные данные о стоимости токенов для поддерживаемых моделей.

# Детализация ВИ
# ВИ-1: Инициализировать хранилище

**Краткое описание:** Разработчик подключается к библиотеке, указывая путь к файлу базы данных SQLite. Если база данных отсутствует, система создает ее и инициализирует необходимую структуру таблиц. Система также настраивает соединение для безопасной конкурентной работы (включает WAL-режим).
**Актор:** Разработчик
**Предусловия:** Библиотека установлена в окружении Python.
**Триггер:** Вызов метода инициализации клиента.

**Основной поток:**
*   Актор передает Системе путь к файлу базы данных db\_path.
*   Система проверяет наличие файла по указанному пути.
*   Файл не существует: Система создает пустой файл базы данных SQLite по указанному пути.
*   Система устанавливает соединение с базой данных.
*   Система конфигурирует соединение (включает режим PRAGMA journal\_mode=WAL; для поддержки конкурентного доступа).
*   Система проверяет наличие необходимой схемы БД.
*   Структура отсутствует: Система выполняет DDL-скрипты для создания таблиц (Prompts, Revisions, Tags, Model\_Tags, Tariffs и др.) и необходимых индексов.
*   Система возвращает Актору объект клиента готовый к работе.

**Альтернативные потоки:**
*   **3а. Ошибка доступа к файловой системе (нет прав на запись или некорректный файл/формат файла):**
    *   Система прерывает инициализацию.
    *   Система возвращает Актору исключение RuntimeError или FileNotFoundError.
*   **6б. Файл существует, но не является валидной базой SQLite:**
    *   Система прерывает инициализацию.
    *   Система возвращает Актору исключение RuntimeError.

**Постусловия:** Соединение с хранилищем успешно установлено, структура БД актуальна, система готова к выполнению CRUD-операций с промптами.

# ВИ-2: Создать промпт

**Краткое описание:** Разработчик передает имя промпта, структуру сообщений и опциональные параметры (описание, теги). Система валидирует данные, проверяет уникальность имени, создает сущность промпта и фиксирует первую версию в виде полного снапшота.
**Актор:** Разработчик
**Предусловия:** Соединение с хранилищем инициализировано и доступно для чтения/записи.
**Триггер:** Вызов API-метода создания нового промпта.

**Основной поток:**
*   Актор передает Системе: уникальное имя промпта (name), структуру сообщений (messages), опциональный комментарий (description), а также опциональные списки тегов (tags) и тегов моделей (model\_tags).
*   Система валидирует входную структуру messages: проверяет, что в каждом сообщении присутствуют обязательные поля role (system, user, assistant и т.д.) и content.
*   Система проверяет в хранилище отсутствие промпта с переданным именем name.
*   Система создает сущность Prompt.
*   Система формирует объект Snapshot (полную копию переданной структуры сообщений), так как первая версия всегда является снапшотом.
*   Система создает сущность Revision:
    *   Присваивает номер версии 1.
    *   Прикрепляет сформированный Snapshot.
    *   Записывает переданный description (или оставляет пустым, если не передан).
    *   Устанавливает текущий timestamp.
*   Система связывает Prompt с созданной Revision, делая ее актуальной (последней) версией.
*   Если переданы списки tags и/или model\_tags, Система подготавливает связи этих тегов с новым промптом.
*   Система сохраняет все новые сущности (Prompt, Revision, Snapshot, связи с тегами) в хранилище (SQLite).
*   Система возвращает пользователю сущность Prompt

**Альтернативные потоки:**
*   **2а. Ошибка валидации структуры сообщений (отсутствует role или content):**
    *   Система прерывает выполнение.
    *   Система возвращает Актору ошибку валидации ValueError.
*   **3а. Промпт с указанным именем уже существует:**
    *   Система прерывает выполнение.
    *   Система возвращает Актору ошибку о конфликте имен KeyError с соответствующим сообщением.
*   **9а. Ошибка записи в базу данных:**
    *   Система откатывает транзакцию.
    *   Система возвращает Актору соответствующую ошибку БД.

**Постусловия:** В базе данных успешно создана запись нового промпта, его первая версия (снапшот) и привязаны теги (если были переданы).

# ВИ-3: Изменить промпт

## Описание
**Краткое описание:** Разработчик передает обновленное содержимое промпта. Система вычисляет разницу с последней версией и фиксирует ее как новую ревизию в истории.
**Актор:** Разработчик
**Предусловия:** Соединение с хранилищем инициализировано и доступно для чтения/записи.
**Триггер:** Вызов API-метода обновления промпта.

**Основной поток:**
1. Актор передает Системе: имя целевого промпта, новую структуру сообщений (`PromptMessages`) и опциональный комментарий (`description`).
2. Система ищет в хранилище сущность `Prompt` по переданному имени.
3. Система извлекает текущую актуальную версию `Revision` найденного промпта.
4. Система получает полное содержимое текущей версии в структуру `PromptMessages`.
5. Система покомпонентно сравнивает новую структуру `PromptMessages` с реконструированной текущей версией.
6. Система вычисляет разницу и формирует объект `MessageDelta` (отражающий добавления, удаления и изменения в ролях/тексте).
7. Система создает новую сущность `Revision`:
    *   Присваивает номер (текущий номер + 1).
    *   Устанавливает ссылку на предыдущую версию (сохранение двусвязного списка).
    *   Прикрепляет объект `MessageDelta`.
    *   Записывает переданный `description` (или оставляет пустым) и текущий timestamp.
8. Система обновляет сущность `Prompt`, назначая новую `Revision` в качестве актуальной и обновляя timestamp изменения промпта.
9. Система сохраняет все изменения в хранилище

**Альтернативные потоки:**
*   **2а. Промпт с указанным именем не найден:**
    1. Система прерывает выполнение.
    2. Система возвращает Актору ошибку.
*   **5а. Изменений не обнаружено (новое содержимое полностью идентично текущему):**
    1. Система прерывает процесс создания новой ревизии.
    2. Система не выполняет запись в БД.
    3. Система возвращает Актору метаданные текущей версии (или статус "Not Modified").
*   **9а. Ошибка записи в хранилище:**
    1. Система откатывает транзакцию (Rollback), возвращая базу данных к состоянию до шага 9.
    2. Система возвращает Актору ошибку соответствующую ошибку.

**Постусловия:** В базе данных сохранена новая версия промпта, связанная с предыдущей, ИЛИ состояние базы данных осталось неизменным (в случае альтернативных потоков).

# ВИ-4: Удалить промпт

**Краткое описание:** Разработчик передает имя промпта для удаления. Система безвозвратно удаляет сам промпт, всю историю его версий (снапшоты, дельты), а также очищает все привязки к тегам и тегам моделей.
**Актор:** Разработчик
**Предусловия:** Соединение с хранилищем инициализировано и доступно для чтения/записи.
**Триггер:** Вызов API-метода удаления промпта.

**Основной поток:**
*   Актор передает Системе имя целевого промпта для удаления.
*   Система ищет сущность Prompt в хранилище по указанному имени.
*   Система открывает транзакцию базы данных.
*   Система удаляет все связи данного промпта с тегами (tags).
*   Система удаляет все связи данного промпта с тегами моделей (model\_tags).
*   Система удаляет все объекты Snapshot и MessageDelta, связанные с версиями этого промпта.
*   Система удаляет все сущности Revision (историю версий) для данного промпта.
*   Система удаляет саму сущность Prompt.
*   Система сохраняет изменения в SQLite.

**Альтернативные потоки:**
*   **2а. Промпт с указанным именем не найден:**
    *   Система прерывает выполнение.
    *   Система возвращает Актору ошибку KeyError, сообщая, что удаляемый объект не существует.
*   **9а. Ошибка записи/удаления в хранилище:**
    *   Система откатывает транзакцию.
    *   Система возвращает Актору ошибку базы данных, состояние хранилища остается неизменным.

**Постусловия:** Промпт и все связанные с ним данные удалены из базы данных.

# ВИ-5: Просмотреть список всех промптов

**Краткое описание:** Разработчик запрашивает список всех промптов. Система извлекает метаданные промптов, вычисляет размер актуальной версии в токенах и, если к промпту привязаны теги моделей model\_tags, рассчитывает примерную стоимость обращения к LLM на основе сохраненных тарифов.
**Актор:** Разработчик
**Предусловия:** Соединение с хранилищем инициализировано и доступно для чтения.
**Триггер:** Вызов API-метода для получения списка промптов.

**Основной поток:**
*   Актор вызывает метод получения списка всех промптов.
*   Система извлекает из хранилища список всех сущностей Prompt вместе с их базовыми метаданными (имя, даты создания/изменения, назначенные tags и model\_tags).
*   Для каждого промпта система определяет его актуальную версию.
*   Система формирует текстовое содержимое актуальной версии и производит подсчет количества токенов.
*   Система проверяет наличие model\_tags у промпта.
*   Если model\_tags присутствуют:
    *   Система извлекает из таблицы тарифов актуальную стоимость токенов для каждой привязанной модели.
    *   Система вычисляет итоговую стоимость промпта для каждой модели (количество токенов \* тариф модели).
    *   Добавляет полученные цены в выходные метаданные промпта.
*   Если model\_tags отсутствуют:
    *   Система добавляет в выходные метаданные только вычисленное количество токенов.
*   Система формирует итоговый список и возвращает его Актору.

**Альтернативные потоки:**
*   **2а. В хранилище нет ни одного созданного промпта:**
    *   Система возвращает Актору пустой список.
*   **6а. Для привязанного model\_tag в системе нет сохраненного тарифа:**
    *   Система пропускает расчет стоимости для этой конкретной модели (или указывает стоимость как null/None).
    *   Добавляет в ответ соответствующее предупреждение (warning).
    *   Продолжает обработку остальных моделей и возвращает список.

**Постусловия:** Актор получил обзорный список промптов с рассчитанными метриками.


# ВИ-6: Просмотреть историю версий

**Краткое описание:** Разработчик запрашивает историю изменений конкретного промпта. Система возвращает список метаданных всех существующих версий этого промпта, отсортированный по номеру версии в порядке возрастания.
**Актор:** Разработчик
**Предусловия:** Соединение с хранилищем инициализировано и доступно для чтения.
**Триггер:** Вызов API-метода получения истории промпта.

**Основной поток:**
*   Актор передает Системе имя целевого промпта.
*   Система ищет сущность Prompt в хранилище по переданному имени.
*   Система выполняет запрос к хранилищу для извлечения всех сущностей Revision, привязанных к найденному промпту.
*   Система извлекает для каждой версии её метаданные: номер версии, дату/время создания (timestamp) и комментарий (description).
*   Система возвращает отсортированный по версиям список метаданных Актору.

**Альтернативные потоки:**
*   **2а. Промпт с указанным именем не найден:**
    *   Система прерывает выполнение.
    *   Система возвращает Актору ошибку KeyError, сообщая, что запрашиваемый промпт не существует.

**Постусловия:** Актор получил отсортированную историю версий промпта.

# ВИ-7: Сравнить версии промпта

**Краткое описание:** Разработчик запрашивает сравнение двух конкретных версий промпта. Система реконструирует обе версии до полного состояния и выполняет покомпонентное сравнение, возвращая структурированный отчет о добавленных, удаленных и измененных сообщениях.
**Актор:** Разработчик
**Предусловия:** Соединение с хранилищем инициализировано и доступно для чтения.
**Триггер:** Вызов API-метода для сравнения двух версий.

**Основной поток:**
*   Актор передает Системе: имя целевого промпта, номер базовой версии (source\_version) и номер целевой версии (target\_version).
*   Система ищет сущность Prompt в хранилище по имени.
*   Система проверяет наличие в истории промпта обеих запрошенных версий (source\_version и target\_version).
*   Система реконструирует полное содержимое source\_version (путем наложения дельт от ближайшего снапшота, аналогично ВИ-16).
*   Система реконструирует полное содержимое target\_version.
*   Система выполняет структурное сравнение списков сообщений обеих версий:
    *   Определяет **удаленные сообщения** (сообщения, присутствующие в source\_version, но отсутствующие в target\_version).
    *   Определяет **добавленные сообщения** (сообщения, отсутствующие в source\_version, но появившиеся в target\_version).
*   Для сообщений, которые сохранились (совпадает позиция и/или роль role), система выполняет текстовое сравнение поля content:
    *   Если текст отличается, система генерирует текстовый diff (разницу на уровне строк/символов) и помечает сообщение как **измененное**.
*   Система формирует структурированный объект отчета (DiffReport), содержащий списки добавлений, удалений и текстовых изменений.
*   Система возвращает сформированный отчет Актору.

**Альтернативные потоки:**
*   **1а. Актор передал одинаковые номера для source\_version и target\_version:**
    *   Система вызывает Warning с соответствующим сообщением о идентичных версиях.
*   **2а. Промпт с указанным именем не найден:**
    *   Система прерывает выполнение.
    *   Система возвращает ошибку KeyError.
*   **3а. Одна или обе указанные версии не найдены в истории:**
    *   Система прерывает выполнение.
    *   Система возвращает ошибку ValueError с указанием отсутствующей версии.
*   **6а. В процессе сравнения выясняется, что содержимое версий абсолютно идентично (разница только в метаданных):**
    *   Система возвращает пустой отчет об изменениях.

**Постусловия:** Актор получил информацию о разнице между версиями.

# ВИ-8: Восстановить промпт из предыдущей версии

**Краткое описание:** Разработчик откатывает промпт к историческому состоянию. Для сохранения линейности истории создается новая версия, содержимое которой идентично выбранной старой версии.
**Актор:** Разработчик
**Предусловия:** Соединение с хранилищем инициализировано и доступно для чтения/записи.
**Триггер:** Вызов API-метода восстановления/отката версии.

**Основной поток:**
1. Актор передает Системе: имя целевого промпта и номер целевой версии `target_version`.
2. Система ищет в хранилище сущность `Prompt` по переданному имени.
3. Система ищет в истории промпта версию с номером `target_version`.
4. Система извлекает актуальную (самую последнюю) версию промпта.
5. Система реконструирует полное текстовое содержимое `target_version` (путем наложения дельт от ближайшего снапшота).
6. Система реконструирует полное текстовое содержимое актуальной версии.
7. Система сравнивает реконструированную `target_version` с актуальной версией и генерирует объект `MessageDelta`. _(Обоснование: технически новая версия должна хранить разницу относительно предыдущей, даже если логически это "откат")._
8. Система создает новую сущность `Revision` (с номером "последняя + 1"), привязывает к ней сгенерированную дельту и указывает ссылку на бывшую актуальную версию.
9. Система обновляет сущность `Prompt`, назначая новую `Revision` актуальной.
10. Система сохраняет изменения в хранилище.

**Альтернативные потоки:**
*   **2а. Промпт с указанным именем не найден:**
    1. Система возвращает соответствующее сообщение об ошибке.
*   **3а. Указанная** **`target_version`** **не найдена в истории промпта:**
    1. Система возвращает соответствующую ошибку.
*   **7а. Содержимое** **`target_version`** **идентично содержимому актуальной версии:**
    1. Система прерывает создание ревизии (откат не имеет смысла, так как состояния равны).
    2. Система возвращает статус "Already at target state".
*   **11а. Ошибка записи в хранилище:**
    1. Система откатывает транзакцию.
    2. Система возвращает соответствующее сообщение об ошибке.

**Постусловия:** История промпта дополнена новой версией, повторяющей содержимое старой версии, без нарушения существующих связей.

# ВИ-9: Добавить тег к промпту

**Актор:** Разработчик
**Предусловия:** Соединение с хранилищем инициализировано и доступно для чтения/записи.
**Триггер:** Вызов API-метода для добавления тега(ов) к существующему промпту.

**Основной поток:**
*   Актор передает Системе имя целевого промпта и список тегов для добавления.
*   Система ищет сущность Prompt в хранилище по переданному имени.
*   Система запрашивает из хранилища текущий список тегов, уже привязанных к данному промпту.
*   Система сравнивает переданный список со списком существующих тегов и выделяет только те теги, которых еще нет у промпта.
*   Система открывает транзакцию базы данных.
*   Для каждого нового тега Система проверяет его наличие в таблице тегов. Если тега там нет - создает его.
*   Система создает связующие записи (отношение многие-ко-многим) между сущностью Prompt и соответствующими записями в таблице Tags.
*   Система сохраняет изменения в базу данных.

**Альтернативные потоки:**
*   **2а. Промпт с указанным именем не найден:**
    *   Система прерывает выполнение.
    *   Система возвращает ошибку KeyError.
*   **4а. Все переданные теги уже присвоены данному промпту:**
    *   Система генерирует предупреждение (Warning), информируя о том, что теги уже существуют.
*   **4б. Часть переданных тегов уже присвоена, а часть - новые:**
    *   Система генерирует предупреждение (Warning) со списком дублирующихся тегов.
    *   Система продолжает выполнение основного потока (шаг 5) только для новых тегов.
*   **8а. Ошибка записи в базу данных:**
    *   Система откатывает транзакцию.
    *   Система возвращает ошибку базы данных.

**Постусловия:** Промпту успешно назначены новые теги. Глобальный словарь тегов обновлен при необходимости.

# ВИ-10: Удалить тег с промпта

**Краткое описание:** Разработчик передает имя промпта и список тегов (или один тег), которые нужно отвязать. Система находит промпт, проверяет наличие связей с этими тегами и удаляет их, не затрагивая сами теги в глобальном реестре.

**Основной поток:**
*   Актор передает Системе: имя целевого промпта и тег (или список тегов) для удаления.

*   Система запрашивает список тегов, фактически привязанных к данному промпту.
*   Система проверяет, что переданные для удаления теги действительно присутствуют в списке привязанных.
*   Система открывает транзакцию.
*   Система удаляет записи из связующей таблицы, соединяющие данный Prompt и удаляемые Tags.

**Альтернативные потоки:**

**Постусловия:** Выбранные теги отвязаны от целевого промпта. Остальные данные хранилища не изменены.

# ВИ-16: Получить промпт для использования

**Краткое описание:** Система извлекает промпт, реконструирует его до запрошенной версии и (опционально) пропускает через адаптер для приведения к формату целевого LLM-фреймворка.
**Актор:** Разработчик
**Предусловия:** Соединение с хранилищем инициализировано и доступно для чтения.
**Триггер:** Вызов API-метода извлечения промпта.

**Основной поток:**
1. Актор передает Системе: имя промпта. Дополнительно (опционально) Актор может передать номер версии (`version`) и идентификатор целевого формата/фреймворка (`adapter_type`).
2. Система ищет сущность `Prompt` по имени.
3. Система определяет целевую `Revision` (если версия передана - ищет ее; если не передана - берет актуальную по ссылке из `Prompt`).
4. Система находит ближайший к целевой `Revision` предшествующий объект `Snapshot` (или сам `Snapshot` первой версии).
5. Система проходит по ссылкам двусвязного списка версий от `Snapshot` до целевой `Revision`, последовательно применяя объекты `MessageDelta`.
6. Система формирует итоговый объект `PromptMessages` (внутренний формат).
7. Система проверяет наличие переданного параметра `adapter_type`.
8. Система загружает соответствующий Адаптер (модуль конвертации).
9. Адаптер конвертирует структуру `PromptMessages` в нативный объект сторонней библиотеки.
10. Система возвращает Актору сконвертированный объект.

**Альтернативные потоки (Alternative Flows):**
*   **2а. Промпт с указанным именем не найден:**
    1. Система возвращает соответствующее сообщение об ошибке.
*   **3а. Переданная** **`version`** **не найдена в истории промпта:**
    1. Система возвращает соответствующее сообщение об ошибке.
*   **7а. Параметр** **`adapter_type`** **не передан или передан как null:**
    1. Система пропускает шаги 8-9.
    2. Система возвращает Актору "сырой" объект `PromptMessages`.
*   **8а. Запрошенный** **`adapter_type`** **не поддерживается или модуль не установлен:**
    1. Система прерывает выполнение.
    2. Система возвращает соответствующее сообщение об ошибке.

**Постусловия:** Запрошенный объект промпта возвращен Актору. Состояние хранилища осталось неизменным.

# ВИ-17: Обновить тарифы моделей

**Краткое описание:** Разработчик инициирует процесс обновления тарифов. Система обращается к внешнему источнику данных, получает актуальную информацию о стоимости токенов для поддерживаемых LLM и сохраняет ее в локальное хранилище.
**Акторы:** Разработчик, Провайдер API
**Предусловия:** Соединение с хранилищем инициализировано и доступно для чтения/записи. Для получения данных из внешнего API требуется доступ в интернет.
**Триггер:** Вызов API-метода для обновления тарифов.

**Основной поток:**
*   Актор вызывает метод обновления тарифов.
*   Система обращается к предопределенному внешнему источнику: делает HTTP-запрос к API.
*   Система получает ответ от внешнего источника, содержащий список моделей и их тарифов.
*   Система парсит полученные данные в JSON формат.
*   Система открывает транзакцию в базе данных SQLite.
*   Для каждой модели из полученного списка:
    *   Система проверяет, существует ли запись для этой модели в локальной таблице тарифов.
    *   Если существует: система обновляет (UPDATE) запись с новыми значениями цен.
    *   Если не существует: система создает (INSERT) новую запись.
*   Система сохраняет все изменения в хранилище.

**Альтернативные потоки:**
*   **2а. Внешний источник данных недоступен (API вернуло ошибку):**
    *   Система прерывает выполнение.
    *   Система возвращает Актору ошибку, связанную с сетевым доступом ConnectionError.
*   **4а. Полученные данные имеют невалидный формат:**
    *   Система прерывает выполнение.
    *   Система возвращает Актору ошибку парсинга данных ValueError.
*   **7а. Ошибка записи в базу данных:**
    *   Система откатывает транзакцию.
    *   Система возвращает Актору соответствующую ошибку БД.

**Постусловия:** Локальная база данных тарифов приведена в актуальное состояние в соответствии с внешним источником.

# Функциональные требования

### Управление промптами
*   Система должна позволять создавать новый промпт с указанием имени и содержимого.
*   При создании промпта система должна принимать опциональный параметр `description` для описания первой версии.
*   Система должна позволять удалять промпт.
*   Система должна позволять обновлять содержимое существующего промпта.
*   При обновлении промпта система должна принимать опциональный параметр `description` для комментария к новой версии.
*   Система должна возвращать ошибку при попытке создания промпта с именем, которое уже существует в хранилище.
*   Система должна позволять читать версию промпта по его идентификатору, где идентификатором является сочетание имени промпта и номера версии.
*   Система должна возвращать список всех промптов с рассчитанной стоимостью для каждой модели, присвоенной промпту через `model_tags`, на основе актуальных тарифов, хранящихся в системе. Для промптов без присвоенных `model_tags` система должна возвращать количество токенов промпта.
### Версионирование
*   Система должна создавать новую версию промпта при явном вызове операции обновления, если передаваемое содержимое отличается от последней сохраненной версии.
*   Система должна хранить поле `description` для каждой версии, содержащее комментарий, переданный при создании или обновлении этой версии. Если комментарий не передан, поле должно быть пустым.
*   Система должна предоставлять возможность получения полного списка версий конкретного промпта, отсортированного по номеру версии в порядке возрастания.
*   Система должна позволять возвращаться к предыдущей версии промпта путем создания новой версии на основе выбранной предыдущей версии.
*   Система должна позволять сравнивать две версии одного промпта и возвращать структурированный список изменений, включая добавленные и удаленные сообщения, а также текстовую разницу внутри сообщений одной роли.
### Формат хранения
*   Система должна поддерживать хранение промптов, состоящих из нескольких сообщений.
*   Система должна валидировать формат входных данных: в каждом сообщении должны присутствовать обязательные поля `role` и `content`.
### Тегирование и поиск
*   Система должна позволять присваивать теги промпту при создании и редактировании.
*   Теги должны присваиваться промпту на глобальном уровне.
*   Система должна позволять удалять тег с промпта.
*   Система должна позволять искать промпты по одному или нескольким тегам, включая логические операции `NOT`, `AND`, `OR`.
*   Система должна позволять искать промпты по полному совпадению имени.
*   Система должна позволять получать список всех тегов, используемых в хранилище.
*   Система должна возвращать предупреждение и успешный результат без изменения состояния хранилища при попытке присвоить тег, уже присвоенный данному промпту.
*   Система должна предоставлять отдельный метод для присвоения тега существующему промпту.
### Теги моделей
*   Система должна позволять присваивать промпту один или несколько `model_tags`.
*   Система должна возвращать ошибку при попытке присвоить промпту `model_tag`, для которого в системе отсутствует тарифная информация.
*   При попытке присвоить `model_tag`, уже присвоенный данному промпту, система должна возвращать предупреждение и успешный результат без изменения состояния хранилища.
*   Система должна позволять удалять `model_tag` с промпта.
*   Система должна возвращать ошибку при попытке удалить `model_tag`, не присвоенный данному промпту.
### Тарифы моделей
*   Система должна предоставлять метод для обновления тарифных данных путем получения актуальных значений из внешнего источника с последующим сохранением в хранилище: перезаписью значений для существующих моделей и добавлением записей для новых.
### Получение промпта для использования
*   Система должна предоставлять метод получения промпта, принимающий имя промпта как обязательный параметр, номер версии как опциональный параметр и идентификатор адаптера `adapter_type` как опциональный параметр.
*   Система должна возвращать промпт в формате `PromptMessages` без конвертации при отсутствии параметра `adapter_type`.
*   Система должна конвертировать `PromptMessages` через соответствующий адаптер и возвращать нативный объект целевого фреймворка при указании параметра `adapter_type`.
*   Система должна возвращать ошибку с явным указанием идентификатора адаптера при запросе неподдерживаемого или неустановленного `adapter_type`.

# Нефункциональные требования

**Надежность**
*   Операции записи должны быть атомарными: при сбое хранилище не должно переходить в некорректное состояние.
*   При одновременном доступе из нескольких потоков система должна сохранять целостность данных и не допускать повреждения хранилища.
**Целостность и неизменность данных**
*   Каждая сохраненная версия промпта должна быть неизменяемой.
*   При сохранении и извлечении система должна сохранять роли сообщений без изменений.
*   При сохранении и извлечении система должна сохранять форматирование содержимого без изменений.
**Интеграции и адаптеры**
*   Система должна поддерживать расширяемую архитектуру адаптеров для конвертации внутреннего представления промпта в форматы сторонних библиотек.
*   При конвертации система не должна изменять семантику содержимого, включая шаблонные переменные.
**Переносимость**
*   Библиотека должна работать на Linux, macOS и Windows.
*   Формат хранилища должен быть переносимым между ОС без конвертации.
*   Минимальная поддерживаемая версия Python 3.10.
**Наблюдаемость**
*   Библиотека не должна самостоятельно конфигурировать обработчики логов.
*   Библиотека должна использовать стандартный механизм логирования Python и передавать управление фильтрацией и выводом логов вызывающему приложению.
**Документация**
*   Библиотека должна иметь документацию, описывающую установку, использование, публичный API, совместимость и ограничения.
